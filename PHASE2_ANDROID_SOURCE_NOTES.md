# Spendwise Phase 2 — Android source notes

This source change keeps the existing React/Vite UI inside the **same Capacitor Android application** (`com.spendwise.app`). It adds native notification/SMS detection, an encrypted local review queue, notification routing to one candidate, and WorkManager sync for explicitly confirmed drafts. It does not publish, deploy, apply SQL, or access the live database. This is a source implementation only: no Android APK build or device test was completed.

## Android setup and private test build

1. Install Android Studio, a supported JDK (the project targets Java 21), Android SDK Platform 36 and build tools, and accept SDK licenses. The Gradle wrapper is checked into the project. This environment had no configured Android SDK and no Android build/device test was run.
2. Configure the existing Vite environment with the Supabase project URL and **publishable/anon key only**. Never put the service-role key in React or Android source. The Android WebView authenticates using the existing Supabase Auth flow; native WorkManager receives the same user's access/refresh tokens through an AES-GCM encrypted app-private store.
3. From the repository root run `pnpm install`, `pnpm typecheck`, `pnpm build`, then `pnpm exec cap sync android`. Open `android/` in Android Studio or run `cd android && ./gradlew assembleDebug`. These Android commands are provided as instructions; they were not executed in this task.
4. Install the debug APK privately on a test phone. Sign in to Spendwise, open the account menu, select the notification sources, explicitly enable them, and use **Open Android notification access settings** to grant notification access. Choose optional SMS only after reviewing its disclosure and granting the Android SMS permission. Android notification access is an operating-system-level permission; Spendwise filters selected package names before extracting notification text.
5. Use Android Settings to revoke notification/SMS permissions or pause detection in Spendwise. If notifications are denied, queued candidates remain reviewable in the app when it is opened. Notification-access approval, source-format accuracy, and runtime permission flows still require device testing.
6. Review `supabase/migrations/20261124160000_detected_expense_idempotency.sql` against the real target schema and a disposable Supabase project before separately approving any application. This task leaves it unapplied. Live-schema drift has not been checked.

## Implemented source behavior

- **One app:** Capacitor bridges the existing React UI to the Android native plugin. Existing manual expense entry and Supabase auth/CRUD code are retained.
- **Notification sources:** SBI YONO (`com.sbi.lotusintouch`), Google Pay India (`com.google.android.apps.nbu.paisa.user`), Super.money (`money.super.payments`), and Android Messages (`com.google.android.apps.messaging`). The source must be selected. Android Messages notifications additionally require SBI context in their displayed text. Package IDs/provider notification wording can differ by installed app version and must be confirmed on a real device.
- **Local filtering and storage:** Notification text is read only after the selected-package check, parsed in memory, and not saved or logged raw. SMS is filtered to SBI-like sender IDs and transaction language. The queue stores normalized fields only, protected by AES-GCM with a key held in Android Keystore. No `READ_SMS` permission is declared; the SMS path uses only `RECEIVE_SMS` and new broadcasts, and is opt-in/off by default. Multipart parts in a broadcast are assembled in memory by sender.
- **Classification:** Clear outgoing/success wording with a recognized amount and SBI context becomes a confirmed debit candidate. Incoming-credit, failed, and pending wording is discarded. Refund/reversal wording becomes a reconciliation candidate, visibly labelled, with Proceed disabled and server-side worker guards. Ambiguous items can be reviewed but cannot be saved until the user checks an explicit statement that they independently verified a successful outgoing SBI debit. This is a heuristic, not bank-authoritative verification.
- **Exact notification routing:** Each alert carries the full SHA-256 fingerprint as an opaque local candidate ID and a unique `spendwise://review/<id>` PendingIntent data URI. MainActivity forwards taps received while foregrounded; React focuses that candidate's editable review, not merely the general list. The alert title is “Payment detected — Add expense?” and includes the amount/merchant when parsed.
- **Proceed/Skip:** Proceed validates the amount/category and uses the new authenticated RPC migration path; it is the only path that creates an expense. The user can edit amount, description, category, date and payment method. Repeated requests use the same fingerprint key, with a unique database receipt per user/key and expense. Skip changes only the encrypted local queue state; it does not call the database or create an expense. Reconciliation candidates cannot Proceed.
- **Offline/background sync:** If the live RPC call fails, the confirmed draft, user ID and user-validation flag are saved in the encrypted local queue. WorkManager has a connected-network constraint, retries transient failures, and uses append-or-replace unique work so a queued request is not dropped behind a running sync. It calls `save_detected_expense` with the publishable key and authenticated user token, never a service-role key. The RPC receipt makes network retries idempotent. When the app is open, it also retries queued rows through the existing authenticated Supabase client. Account IDs are checked before upload.
- **Fallback deduplication:** A UPI reference is normalized into the fingerprint when available. Without one, fingerprinting uses normalized amount, merchant and minute bucket without app/package identity; local candidate insertion also suppresses matching amount/merchant events within two minutes. Identical legitimate purchases close together (especially with an empty merchant) can be collapsed, while changed source timestamps or merchant parsing can still miss a duplicate. Real-world false-positive/false-negative rates are unmeasured.

## Migration review and remaining database verification

The migration is additive: it adds `public.detected_expense_receipts` and `public.save_detected_expense(...)`; it does not alter existing expense rows. The function is **SECURITY INVOKER**, not SECURITY DEFINER. It requires `auth.uid()`, derives `user_id` from that identity, validates the idempotency key and expense values, and relies on the existing `expenses` insert RLS and category/user ownership constraints. Receipt SELECT/INSERT are granted only to `authenticated` with owner-scoped RLS; the insert policy also requires the referenced expense to belong to that user. A unique key and exception subtransaction handle concurrent retries without leaving an extra expense. Public/anon function execution is revoked.

This static review is based on the checked-in schema only. The live Supabase schema, actual role grants, function-owner/table privileges, Postgres execution, and RLS behavior were not queried or tested. Before applying the SQL, verify the existing `expenses` columns and constraints, `categories` foreign-key behavior, and Auth roles in a disposable project. Do not apply this file to production without a separate review and explicit approval.

## Known limitations and incomplete verification

- No Android APK was built; no Kotlin compilation, emulator/device installation, permission dialog test, notification tap test, WorkManager execution test, process-restart test, or SMS test was performed. Android functionality is therefore **not verified**.
- No real, redacted notification/SMS examples were tested. Parsers may miss bank/app wording changes or classify an event ambiguously. Android Messages notification previews may be disabled or hidden by the OS. Not every payment emits a notification or SMS.
- Android `NotificationListenerService` and `RECEIVE_SMS` delivery vary by device/OS, battery optimization, notification visibility and policy. WorkManager is deferrable, not exact-time; its network and token refresh/retry behavior requires device testing. Concurrent refresh-token rotation between the WebView and background worker remains a risk to validate.
- The local-only Skip decision and pending queue are lost if app data is cleared, the app is uninstalled, or the Keystore key becomes unavailable. Device backup is enabled in the existing manifest; verify whether the encrypted preference files should be excluded from backup before release.
- Android SMS permissions can require Google Play policy declaration/review for money-management use. This code makes no assumption that Play approval will be granted. Private APK installation may be more suitable for personal testing but does not guarantee SMS broadcasts on every device.
- Live-schema validation and migration execution were intentionally not performed. Publishing/deployment were intentionally not performed.
