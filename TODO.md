## Approved outcomes

- [ ] **Faithful UI and app navigation:** Reproduce the supplied expense-tracker design without redesigning it. Preserve the existing layouts, colors, typography, spacing, icons, cards, navigation, charts and components as closely as possible. Make screens responsive for mobile and desktop. Ensure navigation between all designed screens works correctly. If a screen or interaction is unclear, resolve it without making major design decisions by assumption.
- [ ] **Onboarding and profile preferences:** Implement the shown onboarding flow for spending goals, payment methods, approximate monthly income, income timing and monthly spending target. Persist completed setup for the signed-in user and allow the user to reach the core app.
- [ ] **Monthly budget management:** Set and edit a monthly budget; maintain separate budgets for different months; display remaining budget; calculate budget utilization percentage.
- [ ] **Daily expense tracking:** Add, edit and delete expenses; select expense date and category; enter amount; add payment method and optional description.
- [ ] **Dashboard:** Display monthly budget, total monthly expenses, remaining balance, spending percentage, daily spending information, recent transactions and category-wise spending.
- [ ] **Reports and insights:** Provide daily, weekly and monthly spending summaries, category-wise expense analysis, previous-month comparisons and monthly transaction history.
- [ ] **Accurate expense calculations:** Total monthly expenses are the sum of expenses in the selected month. Remaining budget is monthly budget minus monthly expenses. Budget utilization is monthly expenses divided by monthly budget times 100. Daily average spending is total expenses divided by elapsed days in the selected month. Use each transaction's actual date; filter by both month and year; changing months updates the entire dashboard; previous months' data remains intact; adding, editing or deleting expenses automatically updates related calculations; handle zero budgets and overspending correctly.
- [ ] **Supabase persistence and security:** Use Supabase for persistent cloud storage. Create `monthly_budgets`, `expenses` and `categories` tables; implement secure authentication and Row Level Security. Store expense records permanently in the database and retrieve them dynamically. Do not use temporary mock data or local hardcoded values as actual transactions. Restrict user data to its owner and never expose a service-role key in client code.
- [ ] **Data export and backup:** Export expenses to CSV and download monthly expense reports. Provide backup and restore functionality if practical.
- [ ] **PWA and responsive delivery:** Make the application responsive and installable as a PWA while retaining the approved visual design.
- [ ] **Portable, no-recurring-cost setup:** Use free-tier services, do not introduce paid APIs or paid database services, do not require a subscription to operate the finished application, make source code portable for independent hosting and avoid unnecessary third-party dependencies. Clearly explain that provider free-tier limits may apply.
- [ ] **Complete source and deployment handoff:** Provide complete source code, database setup instructions and free hosting/deployment instructions.


## Phase 2 — Single Spendwise Android app (approved; local implementation only)

- [ ] **One Android app with the existing Spendwise UI:** Package the existing React/TypeScript/Vite application inside one Capacitor Android app. Preserve the current onboarding, Supabase Auth, dashboard, categories, budgets, manual expense create/edit/delete, history, reports, backup/restore, and design. Do not make a separate companion app. Do not publish or deploy.
- [ ] **Privacy-scoped Android detection:** Add a native notification listener in the same app. Require explicit Notification access and source selection. Filter package names before reading text, parse on device, discard raw notification/SMS text, avoid sensitive logs, and provide a clear Pause detection control. Optional SBI SMS detection is separately off by default; request only RECEIVE_SMS when enabled, never read the inbox, and disclose Google Play review limitations.
- [ ] **Transaction classification and notification:** Detect only sufficiently clear, successful outgoing debit candidates for the standard alert titled “Payment detected — Add expense?” with message “₹[amount] paid to [merchant, if available].” Ignore incoming credits, failed and pending transactions; keep refunds/reversals for reconciliation without creating expenses; retain ambiguous items for review but do not allow them to save as expenses until valid debit status is established. Do not show overlays or full-screen alerts.
- [ ] **Editable review and explicit decision:** Tapping the Android notification opens the relevant candidate inside Spendwise through a secure opaque local ID. Show the alert icon, “Add this as an expense?”, detected amount, merchant/description, date/time, UPI, SBI, reference where available, and category. Allow edits to amount, description, category, date, and payment method. Proceed validates and is the only save action; repeated taps must not duplicate. Skip creates no expense and suppresses repeats locally. Handle denied notification permission with an in-app queue.
- [ ] **Encrypted offline queue and idempotent Supabase save:** Persist only minimal normalized candidates in an app-private encrypted queue protected by Android Keystore. Preserve pending/skip/confirmed-save decisions offline. Retry confirmed requests when network is available, using the existing authenticated Supabase user and a stable idempotency key. Add a narrowly scoped, additive SQL migration with authenticated-user ownership/RLS and atomic insertion into existing expenses; do not alter existing expense rows or manual expenses. Do not apply the migration to the live database.
- [ ] **No-paid-service setup and verified delivery:** Use free/open-source build components only. Provide Android setup/build/private-install/permission instructions, report source-only checks actually run, and state that no APK/device behavior is verified without Android SDK/Gradle/device. Do not push, publish, deploy, or apply database changes under this approval.
